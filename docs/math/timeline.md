# T4. Время, пирамида, список правок, тайминг форматов — заключение PMR

Эталон: `tools/ref/timeline_ref.py` (`--write` пишет векторы, `--ffmpeg` повторяет практическую сверку).
Векторы: `core/src/test/resources/ref/timeline_vectors.json`.
Проверено на ffmpeg 6.1 (aac, libopus, libmp3lame, ac3, eac3, dca), числа ниже — фактические.

## Вердикт: ЕСТЬ ОШИБКИ (в ТЗ: 3 критичных, 6 важных; формулы FR-C1 и FR-10 верны; FR-32/33 — методика добавлена, ред. 2 ТЗ)

Ошибки не в арифметике, а в допущениях:
1. «1 кадр разгона» не хватает для MP3 (из-за bit reservoir) и для Opus (RFC 7845 требует 80 мс).
2. Сырые потоки MP3/AC-3/DTS не умеют скрывать кадр разгона. У MP3 без тега LAME вдобавок слышны 529 сэмплов задержки декодера. Из-за этого проверка FR-23 (±1 мс) для MP3 не пройдёт.
3. ffmpeg 6.1 НЕ обрезает хвост AAC в MP4 при декодировании: CI-проверка FR-25 «длина ±1 сэмпл через ffmpeg» в лоб не пройдёт.

## Найденные проблемы (по убыванию критичности)

- **[КРИТИЧНО] FR-23, MP3: одного кадра разгона мало.** Опыт: отрезок с кадра k (320 кбит/с) декодируется так: кадр 0 — мусор (ошибка −0,3 дБ относительно сигнала), кадр 1 — −15,9 дБ, кадр 2 — бит в бит. Причина — bit reservoir: `main_data_begin` ссылается до 511 байт назад, а кадр i_a−1 нужен целым для перекрытия MDCT.
  → Число кадров разгона W = 1 + r, где r — сколько предыдущих кадров нужно, чтобы покрыть `main_data_begin` кадра i_a−1 (разобрать side info: 9 бит MPEG-1, 8 бит MPEG-2). Минимум W = 2. При низких битрейтах может понадобиться до ~5 кадров.
  У AAC и AC-3 одного кадра хватает (проверено: со 2-го кадра отрезка бит в бит).
- **[КРИТИЧНО] FR-23, Opus: 1 кадр < 80 мс.** RFC 7845 §4.6 требует от декодера пре-ролл не меньше 80 мс (3840 сэмплов при 48 кГц), чтобы декодер сошёлся.
  → Разгон Opus — пакеты суммарно ≥ 3840 сэмплов. В новом файле их скрывает `pre-skip = hidden` (сэмплов от начала первого пакета до A), см. вектор `fr23_fast_trim[opus]`: hidden = 5760.
- **[КРИТИЧНО] FR-23, сырые выходы (.mp3, .ac3, .eac3, .dts) не могут скрыть кадр разгона**, а MP3 без тега LAME/Xing даёт ещё +529 сэмплов (12 мс). Проверка «±1 мс» для MP3 тогда провалится.
  → Для `.mp3` писать первым кадр Xing/LAME «Info» с `delay = hidden − 529` (12 бит, ≤ 4095, то есть hidden ≤ 4624 = 4 кадра по 1152) и `padding = K·1152 − delay − (B−A)`, где K — число аудиокадров без Info (длина по LAME = K·spf − delay − padding = B − A; hidden ≥ 529 обеспечено, т.к. W ≥ 2). Так ffmpeg и MediaExtractor (MP3Extractor читает тег LAME) получают ровно [A, B).
  Для AC-3/E-AC-3/DTS (без метаданных) фактическое начало, показанное пользователю, = начало кадра разгона `s_{i_s} − D`. Первые ~256 сэмплов там будут с артефактом перекрытия. В сообщении нужно честно сдвигать начало на кадр.
- **[КРИТИЧНО для CI] FR-25: ffmpeg 6.1 не обрезает хвост AAC в MP4.** Декодируется 46 080 сэмплов вместо 45 100: начало по `media_time` обрезано верно, хвост последнего кадра — нет, даже при точном elst и `stts` последнего сэмпла = 44.
  → В CI длину брать из `ffprobe -show_entries stream=duration_ts` (45 100 при mvhd = fs), сравнивать первые `duration_ts` декодированных сэмплов. Отдельно проверять поля `elst`/`mdhd`/`stts` своим парсером. Для Ogg Opus ffmpeg обрезает и начало, и хвост (48 100 — точно).
- **[ВАЖНО] FR-25: писать `mvhd.timescale = fs` (= `mdhd.timescale`)**, иначе `segment_duration` грубее сэмпла (при шкале 1000 ошибка до fs/2000 = 22–24 сэмпла). Также писать:
  - `stts`: все по 1024, кроме последнего = `delay + N − (K−1)·1024`, так что Σstts = media_time + N (конвенция ffmpeg);
  - `sgpd/sbgp 'roll'` с roll_distance = −1 (ISO/IEC 14496-12 §10.1, AudioRollRecoveryEntry), как пишет ffmpeg;
  - по желанию `iTunSMPB` для Apple.
  
  Задержку энкодера Android (C2SoftAacEnc/FDK) в ТЗ не знаем — **НЕДОСТАТОЧНО ДАННЫХ**. Её нужно измерить на устройстве корреляцией импульса и записать в DeviceProfile. Для справки: ffmpeg aac — 1024 (измерено), Apple — 2112, libopus — 312.
- **[ВАЖНО] FR-26: риск двойной обрезки на Android.** Codec2 (`CCodecBufferChannel`/`CCodecBuffers`, SkipCutBuffer) сам обрезает `encoder-delay`/`encoder-padding`, если они есть в MediaFormat, переданном в `configure()`. MediaExtractor кладёт их туда из elst/iTunSMPB/LAME. Декодер Opus дополнительно сам отбрасывает pre-skip из csd-1 [предположение, проверить на устройстве].
  → Перед `configure()` удалять `KEY_ENCODER_DELAY` и `KEY_ENCODER_PADDING` из формата, а обрезку делать только в `GaplessTrimmer`. Для Opus/MP3 «уже отброшено декодером» калибровать на эталонных файлах (`assets/selftest`, длины известны: 48 100 / 45 100). Контроль — длина ±0.
- **[ВАЖНО] Приоритет источников на входе (MP4/AAC):**
  1. `elst` (media_time ≥ 0), если mvhd_ts = mdhd_ts или сегмент делится без остатка — длина точная;
  2. иначе длину брать из `iTunSMPB` (поле 4, hex);
  3. иначе из Σstts − media_time, если это в пределах одного тика mvhd от elst (файлы ffmpeg, проверено: 46 124 − 1024 = 45 100);
  4. если нет ни elst, ни iTunSMPB — не обрезать и записать в журнал.
  
  Если elst и iTunSMPB расходятся — верить elst и предупреждать в журнале. MP3: тег LAME (Xing/Info), пропуск = delay + 529. Opus: pre_skip и последняя гранула. Для HE-AAC media_time бывает в шкале частоты ядра (неявная сигнализация SBR, mdhd = 22,05/24 кГц) — тогда пересчитать ×2 к выходной частоте.
- **[ВАЖНО] Нормализация (FR-22) в линейном списке правок пересчитываться не может.** Отмена снимает только последнюю операцию, так что предшествующие правки, пока нормализация в списке, неизменны.
  → G вычисляется один раз при создании операции и **хранится в ней как float32** («заморожен»). Повтор (redo) использует тот же объект и не считает заново — отсюда бит-в-бит. Требование «пересчитывается автоматически» в v1 выполняется само: префикс неизменен. Если появится правка операций в середине списка, G считается заново детерминированно (фиксированный порядок суммирования в float64).
- **[ВАЖНО] Бит-в-бит рендера.** Блочный ленивый `Renderer` обязан выполнять те же float32-умножения в том же порядке, что и последовательное применение операций: `((x·g1)·f2)·G`. Предварительно перемножать коэффициенты нельзя: `x·(g1·f2)` ≠ `(x·g1)·f2` в float32.
  Коэффициенты (g, кривые, G) считаются в double, округляются во float32 и хранятся в операции. Тест: рендер с блоками 1, 7, 4096 и с произвольного `fromSample` = эталонный рендер бит в бит.
- **[ВАЖНО] Ввод конца, равного показанной длительности.** Показанная длительность округлена до мс, поэтому при разборе может получиться n > L (до ⌈fs/2000⌉ сэмплов) и ложная ошибка «выход за длительность».
  → Если `0 < n − L ≤ ⌈fs/2000⌉`, молча прижимать к L. По той же причине при перетаскивании хранить исходное n и не разбирать заново показанную строку: круговой путь n → «мм:сс.ммм» → n теряет до ±fs/2000 сэмплов.
- **[ЗАМЕЧАНИЕ] Дискретизация кривой стыка.** FR-C3 задаёт кривую, но не сетку. Эталон берёт сетку FR-C2: `x_i = i/(N−1)`. На стыке тогда два нулевых сэмпла подряд — безвредно. Если в dsp.md (T3) выбрана другая сетка, эталон меняется в одном месте (`raised_cos_in`). Сетки нужно согласовать до T7.
- **[ЗАМЕЧАНИЕ] Громкость на выделении** меняется скачком на краях — возможен щелчок. ТЗ сглаживания тут не требует. Можно добавить как предложение в backlog.
- **[ЗАМЕЧАНИЕ] xHE-AAC и Vorbis в быстрой обрезке.** USAC можно начинать только с независимого кадра (IPF, `usacIndependencyFlag`, sync sample/`sap`). Vorbis: длина пакета = `bs_prev/4 + bs_cur/4`, нужен разбор режимов.
  → Для v1: быстрая обрезка недоступна для xHE-AAC и Vorbis, либо брать границы только по PTS контейнера.
- **[ЗАМЕЧАНИЕ] Задержка энкодеров raw AC-3/E-AC-3/DTS** (ffmpeg: 256/256/512 сэмплов, измерено) нигде в потоке не записана. Она входит в шкалу пользователя как есть, D = 0. ТЗ (FR-26) это не требует.
- **[ЗАМЕЧАНИЕ] NaN от декодера** ломает min/max (Kotlin `Math.min` распространяет NaN) → в декодере заменять NaN на 0 и писать в журнал.

## Семантика списка правок (эталон `apply_op`)

- **Система координат.** Каждая операция хранит `[a, b)` в сэмплах **результата всех предыдущих операций** — это то, что пользователь видит на волне в момент правки. Полуинтервал: `b` исключается, длина `b − a`.
  Операция неизменяема и содержит все параметры: N стыка в сэмплах, g/G во float32, кривую. Изменение настроек позже уже созданные операции не трогает.
- **trim [a,b):** результат `x[a:b]`, длина `b−a`. Сглаживание только на реально новых границах: fade-in N в начале, если a > 0; fade-out N в конце, если b < L.
- **delete [a,b):** результат `x[:a] ++ x[b:]`, длина `L − (b−a)`. При 0 < a и b < L — fade-out на последних N_L сэмплах левого куска и fade-in на первых N_R правого. При a = 0 только fade-in, при b = L только fade-out. Удалить весь файл (a = 0, b = L) нельзя: «Нельзя удалить весь файл».
- **Короткий кусок (FR-19):** `N_side = min(N, ⌊len_side/2⌋)`, где len — длина куска по эту сторону границы (для trim — `b−a`, обе стороны). Если N_side < 2 — без сглаживания. Пример: L = 1000, delete [300, 900), N = 240 → N_L = 150, N_R = 50, длина 400. Длина файла не меняется никогда. Наложение на старые затухания допустимо: коэффициенты перемножаются.
- **gain [a,b):** `y = x·g32`; без выделения a = 0, b = L. `g32 = float32(10^(dB_десятых/200))`; +6,0 дБ → 1,9952623.
- **fade [a,b):** N = b − a, кривая FR-C2 на сетке `i/(N−1)`. Без выделения: `D = ⌊(d_ms·fs + 500)/1000⌋`, прижать к L; in → [0, D), out → [L−D, L).
- **normalize:** весь файл, G (float32) заморожен. В пиковом режиме `G = 10^(−1/20)/max|x|`; при max|x| = 0 режим недоступен (деление на 0).
- **Первый изменённый сэмпл p** (для пересчёта пирамиды и кэша рендера):
  - delete → `a − N_L` (0, если a = 0);
  - trim → 0, если a > 0, иначе `b − N`;
  - gain/fade → a;
  - normalize → 0.
  
  Пересчитываются блоки уровня k с номерами от `⌊p/B_k⌋` до конца, число блоков `⌈L'/B_k⌉`. Отмена использует p отменяемой операции: префикс у неё тот же.
- **Инвариант «отмена всех → повтор всех = бит в бит».** Он следует из трёх условий: рендер — чистая функция (кэш, операции); операции неизменяемы; в рендере нет ГСЧ (дизеринг только в экспорте, с сидом).

## Пирамида и масштаб

- Уровень k: для каждого канала два массива float32 (min, max) по `⌈L/B_k⌉` блокам. Последний блок неполный и считается по имеющимся сэмплам.
- Память ≈ (L/256)·(4/3)·8·C байт. При 30 мин, 48 кГц, стерео — 7,2 МБ, укладывается в запас FR-10.
- Пиксель x покрывает сэмплы `[s0 + ⌊x·spp⌋, s0 + ⌊(x+1)·spp⌋)`. Блоки — `⌊начало/B⌋ … ⌊(конец−1)/B⌋` включительно: соседние пиксели покрывают все блоки без пропусков.
- Огибающая на экране шире точной не больше чем на один блок B_k с каждой стороны. Точность FR-C8 относится к самой пирамиде, а не к пикселям.
- Масштаб: spp от 1/8 (8 px на сэмпл) до L/ширина. При spp < 256 рисуются сырые сэмплы из кэша рендера.

## FR-7: разрывы PTS

- Время — PTS выходных буферов декодера (`presentationTimeUs`), начало отсчёта — pts₀ первого буфера.
- **Разрыв** (δ > 1 мс): вставить `pos − written` нулей, где `pos = round_half_up(Δpts·fs/10⁶)`.
- **Перекрытие** (δ < −1 мс): отбросить `min(n, written − max(0, pos))` первых сэмплов буфера.
- **|δ| ≤ 1 мс** — дрожание (MKV хранит мс, MP4 видео часто 1/1000), ничего не делать. Граница строгая: ровно +1,000 мс — не разрыв.
- Порядок обработки: заполнение разрывов (на шкале декодера) → обрезка задержки/паддинга (FR-26) → сведение каналов. Ресемплинга на входе нет.

## FR-23: план быстрой обрезки (эталон `fast_trim_plan`)

- **Порядок расчёта:**
  1. Наружные границы A, B — формула 13.
  2. Первый копируемый пакет `i_s`: W кадров разгона (AAC, AC-3, E-AC-3 — 1; MP3 — ≥ 2 по reservoir; Opus — ≥ 3840 сэмплов; FLAC, PCM — 0).
  3. `hidden = A + D − s_{i_s}`.
- **Как скрыть разгон в выходном контейнере:**
  - m4a: `elst.media_time = hidden`, `segment_duration = B − A`. Если i_a = 0, то hidden = D: исходная задержка сохраняется;
  - Ogg Opus: `pre_skip = hidden`, конечная гранула = hidden + (B − A);
  - MP3: тег LAME, см. выше;
  - FLAC: разгона нет. Перенумеровать кадры (фиксированный блок), пересчитать CRC-8/CRC-16, `total_samples` в STREAMINFO, MD5 = 0 (по RFC 9639 «неизвестно»);
  - WAV: точно до сэмпла.
- **Конец:** у AAC/MDCT выход кадра j = перекрытие и сложение (j−1, j), лишний кадр после последнего не нужен.
- **Текст сообщения:** сдвиг = разность ПОКАЗАННЫХ значений в мс, тогда текст согласован сам с собой; при 0 — «совпадает с выделением». Вектор: AAC, D = 2112, fs = 48 000, выделение 1,000–10,000 с → «Фактическое начало 00:00.980 (на 20 мс раньше выделения), конец 00:10.004 (на 4 мс позже).»

## Границы применимости

- Целочисленные формулы точны до 24 ч при 192 кГц (Long). Ввод — не больше 3 знаков дроби; при четырёх и более — ошибка формата (вектор `fr_c1_parse_invalid`).
- Формат ввода: `[[ч:]мм:]сс[.ммм]`. Ведущее поле не ограничено, следующие < 60, запятая допустима. Вывод: `мм:сс.ммм` при < 1 ч, `ч:мм:сс.ммм` при ≥ 1 ч.
- Оценка места верна, только если fs и C известны до декодирования. У HE-AAC выходная частота вдвое больше той, что в контейнере (SBR): брать 2·fs, если профиль HE (или по формату после `INFO_OUTPUT_FORMAT_CHANGED`). Если длительности нет, проверять свободное место по ходу декодирования.
- Задержку энкодеров Android и поведение Codec2 по обрезке нужно измерить на устройстве: это [предположение], пока не откалибровано.

## FR-32: цикл выделения (эталон `loop_fill`, `loop_stream`, `cursor_from_timestamp`)

**Рендер цикла.** Поток для AudioTrack заполняется блоками по `nframes` кадров. Позиция рендера `pos` в координатах результата после правок, цикл — полуинтервал `[start, end)`.
1. Перед каждым блоком: если `pos ∉ [start, end)`, то `pos := start`. Этим покрыты: «Играть» при курсоре вне выделения; новый конец оказался ≤ pos; новое начало сдвинуто правее pos. Последний случай в ТЗ не описан — рекомендую так же переходить к началу, иначе прозвучит невыделенный кусок.
2. Внутри блока: `n = min(осталось, end − pos)` → `Renderer.render(pos, n)` → `pos += n`; при `pos == end` сразу `pos := start`, и тот же блок дозаполняется дальше. Тишина не вставляется, сглаживания нет (Д-15).
3. Цикл `while`, а не один переход на блок: цикл короче блока (вплоть до 1 сэмпла) несколько раз проходит внутри одного блока.

Без выделения цикл = `[0, L)`. Порядок умножений внутри `render` тот же, что в экспорте. Разбиение на куски не влияет на значения сэмплов: рендер — чистая функция позиции. Поэтому стык цикла «95 999 → 48 000» бит в бит равен сэмплам рендера.

**Курсор без накопленной ошибки.** Поставщик ведёт журнал сегментов `(w0, p0, n)`: кадры AudioTrack с номерами `w0 … w0+n−1` содержат сэмплы рендера `p0 … p0+n−1`.
- Курсор: `AudioTrack.getTimestamp(ts)` → `F = ts.framePosition + round_half_up((now − ts.nanoTime)·fs/10⁹)` — номер кадра, звучащего сейчас. Позиция = `p0 + (F − w0)` для сегмента, содержащего F.
- Задержка тракта (буфер AudioTrack + HAL + ЦАП) учитывается автоматически: framePosition — это кадр, который РЕАЛЬНО выходит в момент nanoTime, а не записанный. Отдельно вычитать задержку не нужно и нельзя: получится двойной учёт.
- Ошибка не накапливается по проходам: всё в целых номерах кадров, журнал точный. Остаётся только дрожание метки времени (обычно < 1–5 мс).
- Пока `getTimestamp` возвращает false (первые ~100–200 мс после play/flush), брать `getPlaybackHeadPosition()`: та же шкала кадров, но с задержкой ЦАП. Сегменты старше F удалять.
- Поле `framePosition` — Long. `getPlaybackHeadPosition` — int (беззнаково ~24,8 ч при 48 кГц), переполнение маловероятно, но учитывать как беззнаковое.

**Реакция на смену выделения ≤ 200 мс.** Новые границы действуют с первого НЕзаписанного блока. Записанное, но не проигранное (`w − F`) доиграет. Поэтому `latency_write_ahead + block ≤ 200 мс`: например, буфер AudioTrack ≈ 2× минимального и блок ≤ 20 мс (960 кадров при 48 кГц).
`flush()` не рекомендуется (щелчок и сброс метки времени). Если всё же нужен — допустим только при сдвиге больше 200 мс записанного вперёд, журнал тогда начинается заново.

**Контрольные примеры** (`fr32_loop` в векторах):
- [48 000; 96 000), 5 проходов, блок 4096 → 240 000 кадров, `out[i] = 48 000 + i mod 48 000`. При блоках 1, 7, 48 000, 100 000 результат тот же;
- цикл из 1 сэмпла [10, 11), 5 кадров, блок 3 → [10, 10, 10, 10, 10];
- [0, 3), 8 кадров, блок 5 → [0, 1, 2, 0, 1, 2, 0, 1];
- [0, 2000), блок 500, после 1000 кадров конец := 600 → кадры 1000…1599 = сэмплы 0…599;
- [0, 2000), после 500 кадров выделение := [800, 1000) → с кадра 500 идут 800…999 по кругу;
- курсор: цикл [48 000; 96 000), блок 960, `framePosition = 59·48 000`, `now − nanoTime = 0,5 с` → позиция 72 000 (середина 60-го прохода).

## FR-33: автопроверка сохранённого файла

**Общее.**
- Ожидаемая длина N = длина рендера после ресемплинга (FR-C6: `round(N_in·fs_out/fs_in)` — тот же объект `ExportPlan`, а не пересчёт).
- Время в сообщении — `format_samples(N, fs_out)`.
- В ТЗ два формата: «00:12:34.567» (FR-33) и «00:00.981» (FR-23). Нужен один форматтер на всё приложение. Рекомендую `мм:сс.ммм`, а при ≥ 1 ч — `ч:мм:сс.ммм` [уточнить у пользователя / UI].
- Декодирование для проверки идёт тем же путём, что вход редактора: MediaExtractor → MediaCodec без `KEY_ENCODER_DELAY/PADDING` → `GaplessTrimmer`. Двойная обрезка исключена тем же механизмом, что в FR-26.

| Что | Независимая проверка | Допуск | Обоснование |
|---|---|---|---|
| WAV | Разбор RIFF: fmt (1 = PCM / 3 = float / EXTENSIBLE + subformat), fs, C, bits; `N = data_size / blockAlign`. Если байт в файле меньше, чем `data_size` → «усечён», N = фактические байты / blockAlign. Дополнительно MD5 области data = MD5 байтов, отданных писателю при экспорте (считается потоково) | 0 | Наш писатель, формат без потерь — любое отличие = порча ввода-вывода |
| FLAC | 1) STREAMINFO: fs, C, bps, `total_samples == N`, MD5 ≠ 0. 2) Полное декодирование **системным** декодером Android (c2.android.flac.decoder) → длина = N и MD5 декодированного PCM (RFC 9639: знаковые сэмплы, чередование, LE, ⌈bps/8⌉ байт) = MD5 в STREAMINFO | 0 | См. выбор ниже. **FLAC: чем независимо сверять MD5 — выбор.**
- **Повторный прогон своего энкодера по рендеру — отвергнуто.** MD5 в STREAMINFO и так считается энкодером по входному PCM. Повторный прогон сравнивает энкодер сам с собой: ошибки в предсказании, Rice-кодировании и битовой записи не ловятся. Ловятся только сбои ввода-вывода, а их дешевле ловить побайтным MD5 файла.
- **Свой минимальный FLAC-декодер в `:core`** (CONSTANT/VERBATIM/FIXED/LPC, Rice 4/5 бит, межканальная декорреляция; ~400–600 строк) — независим от телефона, но пишется тем же автором по тому же пониманию RFC. Ошибка трактовки спецификации может повториться и в энкодере, и в декодере. К тому же это ещё один модуль, который надо проверять.
- **Выбрано: системный декодер Android (MediaCodec FLAC)** с `KEY_PCM_ENCODING = ENCODING_PCM_FLOAT` для 24 бит и `PCM_16BIT` для 16 бит. Он независим (чужая реализация, как и плееры пользователя), уже есть на телефоне, кода почти нет, и он проверяет именно то, что услышит пользователь.
  - float → int24 обратимо точно: `v = f·2²³` — целое, 24 бита мантиссы. Функция `float_to_int24_exact` с проверкой целочисленности. Нецелое значение = «декодер не точный» → предупреждение в журнал, проверка только длины.
  - [предположение] поддержку float-выхода FLAC-декодером на API 35 нужно подтвердить прототипом на телефоне. Если не поддерживается — для 24 бит включается свой минимальный декодер как запасной вариант.
- В CI (без телефона) независимый декодер — `flac -t` и ffmpeg, это уже есть в плане.

**Средний битрейт.** `avg = size·8·fs/N`; предупреждение при `|avg/target − 1| > 0,15`. Векторы: 45 МБ за 30 мин при 192 кбит/с → 200 000 бит/с, +4,2 % — норма; 32 МБ → 142 222, −25,9 % — предупреждение.
- [ЗАМЕЧАНИЕ] Opus VBR на тихом материале законно опускается ниже цели. Для коротких файлов (< ~10 с) накладные расходы контейнера (moov, заголовки страниц Ogg) дают ложные отклонения. Рекомендация: для Opus предупреждать только о превышении, для файлов < 10 с не проверять.
- [ЗАМЕЧАНИЕ] Тест «усечён на 10 %»:
  - для m4a от MediaMuxer `moov` пишется в конце → усечённый файл не читается вообще. Сообщение будет «контейнер не читается», а не «длина … вместо …»;
  - сообщение с длиной проверять на WAV, FLAC и Ogg; для m4a — отдельный ожидаемый текст.
