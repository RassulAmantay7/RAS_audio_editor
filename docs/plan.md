### Слои
```
UI (:app/ui, View в коде) ──> EditorController (контракт) ──> EditorSession (:app/editor)
                                                    │
         :app/media (MediaExtractor, MediaCodec, AudioTrack, MediaMuxer)   :app/export (FGS, MediaStore)
                                                    │
                          :core — чистый Kotlin/JVM, без Android (NFR-2)
   time · dsp · loudness · edit (список правок + ЕДИНЫЙ рендер) · peaks · format (WAV/FLAC/MP4/Ogg/кадры) · pipeline · cli
```
- **Единый рендер (FR-13):** `core.edit.Renderer.render(fromSample, dst)` — чистая функция от (кэш PCM, список правок). Плеер и экспорт вызывают один и тот же код, а побитовое совпадение после отмены и повтора (FR-16) следует из чистоты рендера.
- Файл-источник для `:core` абстрагирован как `RandomAccessSource` (чтение по смещению). В `:app` он реализуется через `ParcelFileDescriptor`/`FileChannel`, в тестах — через файл. Так разбор WAV, MP4 (elst/iTunSMPB), MP3 (LAME), Ogg (OpusHead) и сканеры кадров тестируются на JVM.
- Кэш PCM — файл float32 в `cacheDir`, чтение блоками через `FileChannel` в переиспользуемые буферы. Весь PCM в heap не попадает (NFR-8).
- Экспорт: `Renderer` → `Resampler` (FR-C6) → `Quantizer` (FR-C7) → `Sink`. Цепочка собирается в `core.pipeline.ExportPipeline`. Android-часть только подаёт байты в MediaCodec и пишет выход в `OutputStream` MediaStore.

### Ключевое решение: чем писать AAC (.m4a) и Opus (.ogg) с точной длиной (FR-25, ОВ-2)

| | Вариант А: MediaMuxer основной, свои писатели запасные | **Вариант Б: свои писатели в `:core` основные, MediaMuxer запасной** |
|---|---|---|
| Точность | Непонятно, пишет ли MediaMuxer `elst` с `media_time` = задержке и конечную гранулу Ogg. Ни задержку, ни паддинг ему через публичный API не передать, `KEY_ENCODER_DELAY` у писателя может игнорироваться [предположение]. | Полный контроль: `elst`, `media_time`, `pre-skip`, конечная гранула вычисляются по формулам PMR. |
| Проверяемость здесь | Только на телефоне, в конце. | Вся логика контейнера тестируется локально и в CI: AAC-кадры от ffmpeg → наш MP4 → декодирование ffmpeg → сверка длины и сдвига ±1 сэмпл. |
| Объём | Меньше кода. | +~600 строк (MP4: ftyp/moov/trak/edts/elst/stbl/esds/mdat; Ogg: страницы, CRC-32, OpusHead/OpusTags, гранулы). |
| Риск | Может обнаружиться только на устройстве, тогда нужен второй круг. | Тонкости esds для HE-AAC/xHE-AAC при копировании «как есть» (запасной путь — MediaMuxer). |

**Рекомендация — вариант Б.** Для MediaMuxer оставляется переключаемый путь (`DeviceProfile.useMediaMuxerFor{Aac,Opus}`), поэтому смена пути не требует пересборки. Самопроверка на телефоне (T19) прогоняет оба пути и показывает, какой даёт точную длину. MediaMuxer остаётся основным там, где своего писателя нет: Vorbis → WebM, AMR → 3GP.

**FLAC (ОВ-3):** свой FLAC-энкодер в `:core` (fixed-предикторы 0–4 + Rice, partition order подбирается перебором, verbatim как запасной вариант, MD5 в STREAMINFO) — **основной путь**, а не резервный. Причины: (1) MediaMuxer не пишет FLAC, контейнер всё равно свой; (2) у системного энкодера 24 бит и MD5 не гарантированы; (3) FR-25 требует побитового совпадения с рендером, а с собственным квантователем FR-C7 это достижимо только при своём энкодере; (4) он полностью проверяется здесь. Системный энкодер FLAC в самопроверке только проверяется для журнала.

**Задержка энкодера AAC/Opus на телефоне** неизвестна заранее, она зависит от кодека (c2.android.aac.encoder / FDK, c2.android.opus.encoder). Источники по порядку: (1) `KEY_ENCODER_DELAY` в выходном формате энкодера; (2) для Opus — `pre-skip` из OpusHead в csd-0; (3) калибровка самопроверкой: короткий импульсный сигнал → энкодер → наш контейнер → декодер → взаимная корреляция. Результат хранится в `DeviceProfile`.

**Задержка декодера на входе (FR-26):** системные декодеры могут сами отбрасывать часть разгона (например, MP3 — 529 сэмплов, Opus — pre-skip) [предположение]. `GaplessTrimmer` в `:core` получает «заявлено в файле» и «уже отброшено декодером» (из `DeviceProfile`, калибруется на эталонных файлах из `assets/selftest`). Двойная обрезка исключается тестом длины ±0.

## Порядок запуска агентов
1. **Сразу, параллельно:** T1 (главная сессия) ‖ T3 (PMR-DSP) ‖ T4 (PMR-время/форматы) ‖ T6 (FS). Предложения FS показываются пользователю, когда будут готовы, без остановки работы.
2. **После T1:** T2 (главная, контракты; учитывает черновики T3/T4, если они готовы) ‖ T5 (GP, фикстуры).
3. **После T2 — волна A (≤ 3 компилирующих worktree + UID):** T7 (после T3+T4) ‖ T8 (после T3) ‖ T10 (после T4) ‖ T16 (UID, на фейках, идёт долго — до T20).
4. **Волна B:** после T7+T8 → T13 (CFA-DSP, не компилирует тяжело) ‖ T11; параллельно T9 и T17 по мере освобождения слотов.
5. **Волна C:** T18 ‖ T12 (после T8–T11) → T14 (после T10, T11) → T15 (после T9, T12).
6. **После T17+T18:** T19. **После T11, T12, T16–T18:** T20 → T21 (CFA).
7. **Этап 3:** T22 → T23 (телефон, решение G1) → T24 → T25 (только одобренное).

Правила (как в PDF-ридере): перед сдачей каждой задачи — `scripts/check.sh` → `CHECK: OK`; сигнатуры из контрактов не меняются (добавлять можно); после слияния каждой волны — push и зелёный CI до начала следующей. Исправления по замечаниям CFA делает GP в той же зоне файлов, затем CFA перепроверяет.
